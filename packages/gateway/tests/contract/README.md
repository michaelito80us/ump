# Contract Tests for UMP GraphQL Gateway

This directory contains contract tests for the UMP GraphQL Gateway using [Pact](https://pact.io/). Contract tests ensure that the API gateway maintains compatibility with its consumers (mobile app and admin app) by verifying that the provider (gateway) can fulfill the expectations defined by the consumers.

## Overview

Contract testing follows the consumer-driven contract testing pattern:

1. **Consumers** (mobile app, admin app) define their expectations of the provider
2. **Provider** (GraphQL gateway) verifies it can meet those expectations
3. **Pact files** are generated to document the contract between consumer and provider

## Test Structure

```
tests/contract/
├── README.md              # This file
├── setup.ts              # Test environment setup
├── provider.test.ts      # Provider verification tests
└── pacts/               # Generated pact files (from consumers)
    ├── mobile-app-ump-gateway.json
    └── admin-app-ump-gateway.json
```

## Consumer Tests

Consumer tests are located in the respective app directories:

- **Mobile App**: `apps/mobile/__tests__/contract/consumer.test.ts`
- **Admin App**: `apps/admin/__tests__/contract/consumer.test.ts`

These tests define what each consumer expects from the GraphQL gateway and generate pact files.

## Provider Tests

Provider tests (`provider.test.ts`) verify that the GraphQL gateway can satisfy all consumer expectations by:

1. Loading pact files generated by consumers
2. Setting up the gateway with mock data
3. Replaying consumer requests against the real gateway
4. Verifying responses match consumer expectations

## Running Contract Tests

### Prerequisites

1. Ensure all dependencies are installed:

   ```bash
   pnpm install
   ```

2. Build the gateway:
   ```bash
   pnpm run build
   ```

### Running Consumer Tests

Run consumer tests to generate pact files:

```bash
# Mobile app consumer tests
cd apps/mobile
pnpm test __tests__/contract/consumer.test.ts

# Admin app consumer tests
cd apps/admin
pnpm test __tests__/contract/consumer.test.ts
```

This will generate pact files in each app's `pacts/` directory.

### Running Provider Tests

Run provider tests to verify the gateway meets consumer expectations:

```bash
# From the gateway directory
cd packages/gateway

# Run all contract tests
pnpm run test:contract

# Run only provider tests
pnpm run test:contract:provider
```

### Running All Tests

To run both unit tests and contract tests:

```bash
pnpm run test:all
```

## Test Scenarios

### Mobile App Consumer Tests

- **Tournament Queries**: Fetching tournament lists and details
- **Match Queries**: Getting match information and schedules
- **Error Handling**: Network errors, GraphQL errors
- **Authentication**: Requests with user tokens

### Admin App Consumer Tests

- **Tournament Management**: CRUD operations for tournaments
- **Schedule Management**: Updating match schedules and venues
- **Audit Logs**: Fetching administrative audit trails
- **Permission Handling**: Admin-only operations and access control

### Provider Verification Tests

- **Schema Compatibility**: Ensuring GraphQL schema changes don't break consumers
- **Data Consistency**: Verifying response data matches expected formats
- **Error Response Format**: Consistent error handling across all operations
- **Authentication Flow**: Proper JWT token validation and authorization

## Pact Files

Pact files are JSON documents that describe the contract between consumer and provider. They contain:

- **Consumer name**: Which app is making the request
- **Provider name**: The GraphQL gateway
- **Interactions**: Expected request/response pairs
- **Matchers**: Flexible matching rules for dynamic data

### Example Pact File Structure

```json
{
  "consumer": { "name": "mobile-app" },
  "provider": { "name": "ump-gateway" },
  "interactions": [
    {
      "description": "a request for tournaments",
      "providerState": "tournaments exist",
      "request": {
        "method": "POST",
        "path": "/graphql",
        "body": {
          "query": "query GetTournaments { tournaments { id name status } }"
        }
      },
      "response": {
        "status": 200,
        "body": {
          "data": {
            "tournaments": [
              {
                "id": "1",
                "name": "Test Tournament",
                "status": "PUBLISHED"
              }
            ]
          }
        }
      }
    }
  ]
}
```

## Best Practices

1. **Keep Tests Focused**: Each test should verify a specific interaction
2. **Use Matchers**: Use Pact matchers for flexible data validation
3. **Provider States**: Set up appropriate data states for each test scenario
4. **Error Testing**: Include tests for error conditions and edge cases
5. **Regular Updates**: Update contract tests when API changes are made

## Troubleshooting

### Common Issues

1. **Pact files not found**: Ensure consumer tests have run and generated pact files
2. **Provider state setup**: Verify mock data matches what consumers expect
3. **Schema mismatches**: Check that GraphQL schema changes are backward compatible
4. **Authentication errors**: Ensure test tokens have appropriate permissions

### Debug Mode

To run tests with verbose logging:

```bash
DEBUG=pact* pnpm run test:contract
```

### Cleaning Up

To clean generated files:

```bash
# Remove pact files
rm -rf pacts/

# Remove logs
rm -rf logs/
```

## Integration with CI/CD

Contract tests should be integrated into your CI/CD pipeline:

1. **Consumer tests** run when consumer code changes
2. **Provider tests** run when provider code changes
3. **Pact files** are shared between consumer and provider builds
4. **Breaking changes** are detected before deployment

For more information about Pact and contract testing, visit [pact.io](https://pact.io/).
